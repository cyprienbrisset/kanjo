Kanjō — Documentation utilisateur

Lire, valider, convertir, réparer, comparer et rendre lisibles vos factures électroniques — Factur-X, UBL 2.1, CII, XRechnung, Peppol, FatturaPA, UN/EDIFACT et Order-X — depuis une seule implémentation, à travers trois interfaces : ligne de commande, terminal et application de bureau.

Dépôt GitHub Site de présentation
Ce document est téléchargeable : utilisez le bouton « Télécharger en PDF » (impression navigateur → « Enregistrer au format PDF ») pour obtenir une version hors-ligne. La mise en page est optimisée pour l'impression.

1. Présentation

Kanjō (勘定, « le compte ») est un outil multiplateforme dédié à la manipulation des factures électroniques. Il s'adresse aussi bien au comptable qui veut lire et vérifier une facture reçue, qu'à l'équipe technique qui automatise la conversion de milliers de documents.

Trois interfaces, un seul cœur :

InterfacePour qui / quandLancement
CLI (ligne de commande)Automatisation, intégration, CI/CD, traitement en lotkanjo <commande>
TUI (interface texte)Inspection interactive rapide au terminalkanjo tui ou kanjo
Studio (bureau)Usage quotidien par un comptable, sans terminalkanjo studio
Principe fondateur — honnêteté. Kanjō ne déclare jamais une conformité qu'il n'a pas calculée : aucun sceau « conforme » sans exécution effective des règles, aucune conformité PDF/A sans validation. Le traitement est 100 % local : aucun appel réseau, aucune télémétrie.

2. Concepts clés

Le modèle pivot

Tous les formats sont traduits vers un modèle pivot unique, aligné sur la sémantique EN 16931 (les « BT », Business Terms, et « BG », Business Groups). Ajouter un format, c'est écrire un lecteur et un écrivain vers ce pivot — jamais un convertisseur direct de format à format. Conséquence pratique : toute conversion passe par le pivot, et une même facture peut être lue en CII et réécrite en UBL sans perte.

Détection par le contenu

Kanjō identifie le format en inspectant le contenu du fichier (octets magiques, racine XML, espaces de noms), jamais uniquement l'extension. Un .xml mal nommé sera correctement reconnu.

Exactitude des montants et des dates

Les montants sont manipulés en arithmétique entière exacte (unités mineures + échelle + devise) — jamais en float64. Les dates de facture sont des dates civiles sans fuseau horaire. Aucune erreur d'arrondi n'est introduite.

Rapport de perte

Une conversion qui perdrait de l'information produit un rapport de perte explicite. La politique --max-loss décide si une conversion dégradante est autorisée, refusée, ou signalée.

3. Installation

Binaires précompilés (recommandé)

Téléchargez l'archive de votre plateforme depuis la page Releases (Linux, macOS, Windows · amd64/arm64), vérifiez l'empreinte, décompressez : le binaire kanjo est autonome, sans dépendance d'exécution.

# Vérifier l'intégrité puis décompresser (exemple Linux amd64)
sha256sum -c SHA256SUMS.txt
tar xzf kanjo_linux_amd64.tar.gz
./kanjo version

Compilation depuis les sources

Kanjō est écrit en Go et se compile en un binaire statique (pur Go, CGO_ENABLED=0) sur six cibles.

CGO_ENABLED=0 go build -o kanjo ./cmd/kanjo
# Client lourd de bureau (fenêtre native, nécessite cgo/WebKit)
CGO_ENABLED=1 go build -o "Kanjō Studio" ./cmd/kanjo-studio
Vérifiez votre environnement à tout moment avec kanjo doctor (voir § doctor).

4. Démarrage rapide

Cinq commandes pour couvrir l'essentiel :

kanjo inspect facture.pdf                 # résumé lisible d'une facture
kanjo validate facture.xml               # vérifier la conformité EN 16931
kanjo convert facture.pdf --to ubl --out ./sortie
kanjo diff facture.pdf facture.ubl.xml   # prouver une conversion sans perte
kanjo render facture.xml                 # produire la face lisible (HTML)

5. Ligne de commande (CLI)

La forme générale est kanjo <commande> [options] [fichiers…]. La plupart des commandes acceptent un fichier, plusieurs fichiers, ou un dossier (avec --recursive).

Options globales fréquentes

OptionEffet
--format table|jsonFormat de sortie. Par défaut : table sur un terminal, json quand la sortie est redirigée (idéal pour scripts/CI).
--helpAide détaillée d'une commande : kanjo <commande> --help.

5.1 inspect — inspecter un document

Affiche une synthèse lisible, la valeur d'un terme métier précis, ou le pivot complet.

OptionDescription
--show summary|terms|jsonNiveau de détail (défaut : summary).
--term BT-112Afficher un Business Term précis.
--format table|jsonFormat de sortie.
$ kanjo inspect facture.xml
▸ F2026-0001  (cii / en16931)
  Type          380 (Facture commerciale)
  Émission      2026-09-14
  Devise        EUR
  Émetteur      SA Meunier  (TVA FR81627131848)
  Destinataire  Société Cliente
  Lignes        2
  Total HT      299.61 EUR
  Total TVA     59.92 EUR
  Total TTC     359.53 EUR
  Net à payer   359.53 EUR

# Valeur d'un terme précis
$ kanjo inspect facture.xml --term BT-112
# Pivot complet en JSON
$ kanjo inspect facture.xml --show json

5.2 validate — valider la conformité

Applique le moteur de règles EN 16931 natif (et les CIUS françaises) au document. Le verdict est réellement calculé, jamais simulé.

OptionDescription
--rules en16931,cius.fr,kanjoJeux de règles à appliquer (défaut : tous ceux applicables au type de document).
--severity error|warningSeuil d'échec (défaut : error).
--explainAfficher le texte intégral des règles échouées (attendu / trouvé).
--report fichier.html|.jsonÉcrire un rapport de validation imprimable.
--recursive, --include, --excludeParcours de dossiers et filtres glob.
--cross-checkConfronter le verdict à des validateurs externes (Mustangproject, KoSIT) s'ils sont configurés.
$ kanjo validate facture.xml
✓ facture.xml  [cii]

✓ 1   ⚠ 0   ✗ 0

# Valider un dossier entier et produire un rapport HTML
$ kanjo validate ./factures --recursive --report rapport.html

# Détail des règles échouées
$ kanjo validate facture.xml --explain
Le code de sortie reflète le verdict (voir § codes de sortie) : idéal pour bloquer une chaîne d'intégration sur une facture non conforme.

5.3 convert — convertir d'un format à un autre

Convertit une ou plusieurs factures via le modèle pivot, avec rapport de perte et politique de perte.

OptionDescription
--to cii|ubl|facturx|xrechnung|peppol|fatturapa|edifact|orderx|jsonFormat cible (requis).
--out fichier|dossierSortie (fichier pour une entrée unique, dossier pour un lot).
--profile minimum|basicwl|basic|en16931|extendedProfil Factur-X (défaut : en16931).
--syntax ubl|ciiSyntaxe pour XRechnung.
--max-loss none|minor|anyPolitique de perte (défaut : minor).
--allow-lossAutoriser explicitement une conversion dégradante.
--workers N, --recursive, --resumeLot : parallélisme, récursivité, reprise d'un lot interrompu.
--preset nomAppliquer un jeu de réglages enregistré (voir preset).
# Une facture Factur-X vers UBL
$ kanjo convert facture.pdf --to ubl --out ./sortie

# Lot : tout un dossier vers Factur-X, 8 workers, reprise possible
$ kanjo convert ./entrantes --to facturx --out ./facturx -w 8 --recursive --resume

# Vers XRechnung en syntaxe CII
$ kanjo convert facture.xml --to xrechnung --syntax cii --out ./x

5.4 extract — extraire le XML d'une Factur-X

Extrait le XML de facture (et, au besoin, les pièces jointes) embarqué dans un PDF Factur-X/ZUGFeRD.

OptionDescription
--stdoutÉcrire le XML sur la sortie standard.
--out dossierDossier de sortie.
--attachmentsExtraire aussi les pièces jointes additionnelles.
--xml-onlyN'extraire que le XML principal (défaut : activé).
$ kanjo extract facture.pdf --out ./xml
$ kanjo extract facture.pdf --stdout > facture.xml

5.5 embed — embarquer un XML dans un PDF

Produit une Factur-X en associant un XML de facture à un PDF, avec l'association exigée par PDF/A-3 (/AF, /AFRelationship).

OptionDescription
--xml fichierXML de facture à embarquer (requis).
--out fichierPDF de sortie.
--name factur-x.xmlNom de la pièce jointe embarquée.
--verify-pdfaValider la conformité PDF/A-3b avec veraPDF (si installé).
$ kanjo embed modele.pdf --xml facture.xml --out facture-x.pdf --verify-pdfa
La conformité PDF/A-3b n'est déclarée que si veraPDF l'a effectivement confirmée ; sinon le rapport l'indique explicitement.

5.6 diff — comparer deux documents

Compare sémantiquement deux factures, quels que soient leurs formats, et distingue les pertes des divergences. Idéal pour prouver qu'une conversion est sans perte.

OptionDescription
--semanticComparaison sur le pivot (défaut : activé).
--ignore BT-9,BT-112Exclure des termes de la comparaison.
--ignore-formattingNormaliser nombres et dates avant comparaison.
$ kanjo diff facture.pdf facture.ubl.xml
$ kanjo diff avant.xml apres.xml --ignore-formatting --ignore BT-9

5.7 repair — corriger les anomalies sûres

Applique des corrections sûres (jamais d'invention de donnée métier) : le document reste fidèle, seules les anomalies non ambiguës sont réparées.

OptionDescription
--dry-runLister les corrections sans les appliquer.
--fixes …Restreindre aux corrections nommées (défaut : toutes les sûres).
--backupConserver l'original en .bak (défaut : activé).
$ kanjo repair facture.xml --dry-run   # aperçu
$ kanjo repair facture.xml             # applique + .bak

5.8 anonymize — anonymiser (RGPD)

Remplace de façon déterministe les données personnelles pour produire un fichier partageable (support, tickets, corpus de test) sans donnée réelle.

OptionDescription
--seed graineGraine pour un remplacement déterministe et reproductible.
--keep amountsPréserver certains aspects (ex. montants) — répétable.
--out dossierSortie (défaut : à côté, suffixe .anon).
$ kanjo anonymize facture.xml --seed demo --keep amounts

5.9 render — face lisible (HTML)

Produit une représentation lisible d'une facture, dans le design de l'application, éventuellement scellée d'un cachet reflétant le résultat de validation.

OptionDescription
--lang fr|en|deLangue de rendu (défaut : fr).
--sealApposer un sceau reflétant la validation.
--out dossierDossier de sortie.
$ kanjo render facture.xml --lang fr --seal

5.10 generate — corpus synthétique

Génère des factures synthétiques cohérentes et reproductibles, pour tester une chaîne sans donnée réelle.

OptionDescription
--count NNombre de factures (défaut : 10).
--scenario …simple, multi-tva, avoir, autoliquidation, intracommunautaire, acompte.
--format cii|ubl|xrechnung|peppol|json|csvFormat de sortie (défaut : cii).
--invalidProduire des cas volontairement non conformes.
--seed NGraine (reproductibilité).
--out dossierDossier de sortie (requis).
$ kanjo generate --count 50 --scenario multi-tva --out ./corpus

5.11 watch — surveiller un dossier

Surveille un dossier « boîte de réception » et traite automatiquement les fichiers déposés selon un preset.

OptionDescription
--preset nomPreset à appliquer (requis).
--out, --done, --failedDossiers de sortie, des fichiers traités et des échecs.
--poll 2sIntervalle de scrutation.
--onceTraiter l'existant puis sortir.
$ kanjo watch ./inbox --preset vers-ubl --out ./inbox/out

5.12 preset — réglages réutilisables

Enregistre des combinaisons d'options réutilisables (par convert, watch…).

$ kanjo preset list
$ kanjo preset save vers-ubl --to ubl --profile en16931
$ kanjo preset show vers-ubl
$ kanjo preset export vers-ubl > vers-ubl.json
$ kanjo preset import vers-ubl.json
$ kanjo preset delete vers-ubl

5.13 library — bibliothèque locale

Indexe les documents traités dans une base SQLite locale pour les retrouver (rétention, droit à l'effacement RGPD).

$ kanjo library index ./factures --recursive
$ kanjo library list
$ kanjo library forget <id>     # droit à l'effacement
$ kanjo library purge --before 2025-01-01

5.14 audit — journal d'audit

Consulte le journal d'audit horodaté et chaîné (tamper-evident) : chaque entrée référence l'empreinte de la précédente, ce qui permet de détecter toute modification. Le journal ne contient aucune donnée personnelle.

$ kanjo audit list
$ kanjo audit verify                       # contrôle d'intégrité de la chaîne
$ kanjo audit export --from 2026-01-01 --to 2026-06-30 --format html --out audit.html
$ kanjo audit path                         # emplacement du journal

5.15 doctor & version

doctor diagnostique l'environnement (OS, capacités optionnelles : Ghostscript, Java, veraPDF). version affiche les trois versions suivies : outil, jeu de règles, schéma de sortie.

$ kanjo version
{
  "tool": "v0.1.0",
  "rules": "2026.3",
  "schema": "github.com/cyprienbrisset/kanjo/1"
}

$ kanjo doctor
  os / arch        darwin / arm64
  java             ✓ /usr/bin/java   (validateurs externes optionnels)
  ghostscript      ·  (conversion PDF/A optionnelle)

6. Interface texte (TUI)

La TUI offre une inspection interactive sans quitter le clavier. Lancez-la sur un dossier ou un fichier :

kanjo tui ./factures      # ou simplement : kanjo

Navigation

ToucheAction
↑ / ↓ (ou k / j)Se déplacer dans la liste des documents.
EntréeOuvrir le document sélectionné (synthèse + termes).
TabBasculer entre les panneaux (liste ↔ détail).
/Filtrer / rechercher dans la liste.
vValider le document affiché.
?Afficher l'aide contextuelle.
qQuitter.
La TUI est idéale pour trier rapidement un lot reçu : on parcourt, on inspecte, on valide, sans écrire une seule commande.

7. Studio (application de bureau)

Studio est l'interface graphique locale, pensée pour un usage quotidien par un comptable, sans terminal. Lancez :

kanjo studio      # ouvre l'application (client lourd natif ou dans le navigateur)

Ce que permet Studio

ÉcranUsage
InspecteurOuvrir une facture (glisser-déposer), lire sa synthèse, ses termes BT et sa face lisible.
ValidationLancer la validation EN 16931 / CIUS et parcourir les anomalies, avec explication règle par règle.
ConversionConvertir vers un autre format avec aperçu du rapport de perte avant écriture.
ComparaisonComparer deux documents (diff sémantique) pour prouver une conversion sans perte.
BibliothèqueRetrouver les documents déjà traités (base locale), avec rétention et effacement RGPD.
Journal d'auditConsulter et exporter le journal chaîné, sans donnée personnelle.

Flux type dans Studio

  1. Glissez une facture (PDF Factur-X, XML UBL/CII…) dans la fenêtre.
  2. Lisez la synthèse et la face lisible dans l'inspecteur.
  3. Lancez la validation : les anomalies s'affichent avec leur explication.
  4. Si besoin, convertissez vers le format attendu ; vérifiez le rapport de perte.
  5. Le traitement est journalisé dans l'audit ; le document rejoint la bibliothèque.
Comme la CLI et la TUI, Studio est 100 % local : vos factures ne quittent jamais votre poste.

9. Conformité EN 16931

Kanjō couvre 100 % des 223 règles du Schematron officiel du CEN, mesurées à chaque commit (aucun stub, chaque règle réellement calculée et éprouvée sur un corpus réel). Le détail par famille est publié dans le rapport de conformité. La conformité n'est jamais déclarée sans avoir été calculée.

10. Codes de sortie

Les commandes renvoient un code de sortie normalisé, pratique en CI :

CodeSignification
0Succès.
1Erreur interne inattendue.
2Erreur d'usage (options invalides).
3Validation échouée (anomalie ≥ seuil).
4Fichier illisible / format non reconnu.
5Conversion dégradante refusée.
6Dépendance/capacité indisponible (XSD, Ghostscript, veraPDF).
7Interruption utilisateur.
8Quota / limite dépassée.

11. Sécurité & RGPD

  • 100 % hors-ligne — aucun appel réseau, aucune télémétrie ; vos factures restent sur votre poste.
  • XML durci — protection contre les attaques XXE et les bombes de décompression.
  • Écriture atomique — jamais d'écrasement partiel ; l'original n'est pas modifié en place.
  • Anonymisation — anonymize pour partager sans donnée personnelle.
  • Journal d'audit sans PII — horodaté, chaîné (tamper-evident), sans aucune donnée métier.
Pour toute question de sécurité ou de conformité impliquant des données sensibles, rapprochez-vous de votre RSSI.
